## Context

Сегодня инвентаризация устройств и контролов реализована в `scripts/real-mqtt-verify.mjs`: импортирует собранный `dist/`, подписывается на `/devices/#`, печатает сводку. Запуск возможен только из дерева разработки после `npm run build`; дефолтный брокер зашит в скрипт (`192.168.55.15`). Пользовательский конфиг Matterbridge для плагина хранится в JSON (в документации: `~/.matterbridge/matterbridge-wirenboard-plugin.config.json`), с теми же полями `mqttHost`, `mqttPort`, `mqttProtocol`, учётные данные и пути TLS, что и у плагина.

## Goals / Non-Goals

**Goals:**

- Один **entrypoint**, устанавливаемый с пакетом (`npm install -g` или локальный `node_modules/.bin`), пригодный для запуска **на контроллере WB** рядом с уже настроенным Matterbridge.
- **Дефолтное подключение к MQTT** из файла конфигурации плагина (тот же JSON, без дублирования параметров вручную).
- Ясный **приоритет** источников: явные аргументы CLI и переменные окружения перекрывают файл; при отсутствии файла — безопасные встроенные дефолты (например `localhost:1883`), согласованные со спекой плагина.
- Сохранить семантику текущего verify-скрипта (канонический порядок контролов, подсчёт mappable через `findMapping`).
- **Аналитика конфига:** после загрузки JSON плагина использовать **релевантные ключи** (см. раздел **Scope аннотаций** ниже) для **пометок в выводе**, чтобы пользователь видел, как настройки соотносятся с MQTT и с регистрацией в Matter. Обход брокера — **полный**; фильтры **не отсекают** строки инвентаризации, а дают флаги/пояснения.
- **Помощь в авторинге конфига:** вывод и **`--json`** должны позволять **скопировать** идентификаторы устройств/контролов в `whiteList` / `blackList` / `deviceOverrides`; в **README** — явный мини-workflow и примеры фрагментов JSON (без генератора «магического» конфига в CLI — это non-goal).
- Дополнительно: флаг **`--json`** — JSON-вывод для автоматизации; краткий **`--help`**.
- **Принцип реализации:** **максимальное реиспользование кода плагина** — CLI импортирует те же модули (`WirenboardMqtt`, `findMapping`, `sortedControlsByCanonicalName`, `normalizeDeviceOverridesEntry`, предикаты префиксов и т.д.). Повторять бизнес-правила в CLI **нельзя**; если нужная логика сейчас только внутри `module.ts` / платформы Matterbridge — **рефакторинг:** вынести чистые функции или тонкие фасады в `src/`, использовать и плагин, и CLI. Исключение — внешняя граница Matterbridge API (`validateDevice`): один **общий адаптер** в репозитории (с тестом на соответствие), без второй реализации «на память».

**Non-Goals:**

- Дублирование правил регистрации, маппинга и разбора `deviceOverrides` в отдельном файле только ради CLI.
- Изменение протокола MQTT или логики маппинга в плагине.
- Отдельный deb-пакет или systemd-unit только для этого CLI (достаточно npm `bin`).
- Интеграция с веб-UI Matterbridge.
- **Полная автогенерация** файла конфига плагина «с нуля» или интерактивный мастер — вне scope; достаточно документированных примеров + машиночитаемого **`--json`**.

## Decisions

1. **Имя команды и `package.json#bin`**
   Использовать имя **`mb-wirenboard-verify-mqtt`** (префикс `mb-` — Matterbridge; узнаваемая связь с текущим `verify:mqtt`).

2. **Реализация entrypoint и общий код**
   **Скомпилированный** ESM из `src/`: тонкий слой CLI (argv, пути конфига, печать) + **импорты из существующих модулей плагина**. Любая логика, которой нет в экспортируемых функциях, **выносится рефакторингом** из `module.ts` / `wirenboardDevice.ts` в общие модули (например предикаты «регистрировать ли устройство», разбор title для `validateDevice`, цепочка «есть ли mappable контрол после skip/hidden»), после чего платформа и CLI вызывают одни и те же функции. Скрипт `verify:mqtt` — обёртка над тем же entrypoint; `scripts/real-mqtt-verify.mjs` удалить или оставить одну строку `node dist/...` без дублирования логики.

3. **Загрузка конфига**
   Читать JSON с диска целиком (один объект на выбранный путь).

   **MQTT-подключение:** извлекать поля, совместимые с `WirenboardMqttConfig` (`mqttHost`, `mqttPort`, `mqttProtocol`, `mqttUsername`, `mqttPassword`, `mqttCaPath`, `mqttCertPath`, `mqttKeyPath`) для соединения с брокером.

   **Обогащение вывода (остальные ключи):** не игнорировать — использовать для **аннотаций**, как конфиг влияет на результат Matterbridge для каждого устройства и контрола. Правила **должны совпадать с плагином** (те же предикаты/нормализация, что в `module.ts` / `deviceOverrides.ts` / `wirenboardDevice.ts`); при расхождении приоритет — поведение плагина.

   Минимальный набор аннотаций:
   - **`ignoreSystemPrefixedDevices`**, **`ignoreNetworkPrefixedDevices`:** пометка на **устройстве**, если сработал бы `shouldSkipMatterRegistration` (как в плагине).
   - **`includeHidden`:** на **контроле** — виден ли канал при текущем значении (`meta.hidden` / внутренние эвристики как в `WirenboardDevice.create`); при `includeHidden: true` явно указать, что скрытые **включаются** в обработку (и наоборот при `false`).
   - **`deviceOverrides`:** после `normalizeDeviceOverridesEntry` — для устройства показать `displayName` override; для контрола пометки **`skip: true`**, **`deviceType`** override (разрешённое имя типа / предупреждение при неизвестном); невалидные записи — как в плагине (warn-сообщения можно отразить в выводе или в JSON поле `configWarnings`).
   - **`whiteList` / `blackList`:** **не** ограничивают обход MQTT. Пометка на устройстве: прошёл бы ли `validateDevice([deviceTitle, serial])` из Matterbridge — **тот же `deviceTitle`**, что в `registerWbDevice` (`deviceOverrides.<id>.name` при наличии, иначе title из meta). Алгоритм: blacklist имеет приоритет; при непустом whitelist нужно совпадение **хотя бы одной** из переданных строк со списком.
   - **`discoveryMode` + `devices`:** обход MQTT полный; при `discoveryMode: "static"` добавить информационную пометку — входит ли id устройства в массив `devices` (ожидание на старте плагина), **без** трактовки как фильтра регистрации, если в коде плагина иначе — зафиксировать в реализации фактическое поведение `registerDiscoveredDevices` и отразить в help и **в README плагина** (при необходимости поправить устаревшую формулировку про «только список устройств»).
   - **`groupingMode`:** **сессионная** пометка (заголовок или блок «effective config»): текущее значение `device` vs `control` и кратко — как это меняет **топологию Matter** (одно bridged-устройство на WB-устройство с дочерними эндпоинтами vs отдельное bridged-устройство на каждый контрол). Не дублировать на каждую строку контрола, если достаточно одного сводного блока + ссылка в README.

   **Scope аннотаций (in scope) vs прочие ключи (out of scope для пометок в v1):**

   | In scope (аннотации / диагностика проброса)                                                                                                                         | Out of scope v1 (не влияют на аннотации; перечислить в README как «не диагностирует CLI»)                                      |
   | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
   | MQTT-поля (только подключение), `includeHidden`, префиксы system/network, `whiteList`/`blackList`, `deviceOverrides`, `discoveryMode`+`devices`, **`groupingMode`** | `failsafeCount`, `discoveryTimeout`, `discoveryIdleMs`, `unregisterOnShutdown`, `wirenboardUrl`, иные поля UI/жизненного цикла |

   При расширении продукта список in scope можно расширять отдельным change.

   **Без `--config`:** перебирать **упорядоченный** список стандартных путей для контроллера Wiren Board и взять **первый** существующий **читаемый** файл. Минимальный состав (имя файла везде `matterbridge-wirenboard-plugin.config.json`):
   1. `/root/.matterbridge/matterbridge-wirenboard-plugin.config.json` — типичный случай Matterbridge под root на WB.
   2. `${HOME}/.matterbridge/matterbridge-wirenboard-plugin.config.json` (через `os.homedir()` / `HOME`) — пользовательская установка или запуск CLI тем же пользователем, что и Matterbridge.

   Если один и тот же путь встречается дважды (например root и `HOME=/root`), дедуплицировать при переборе.

   **`--config <path>`:** не выполнять поиск по списку; загрузить только указанный файл (ошибка, если не задан явно и файл битый — см. спеку).

   Опционально: переменная окружения для пути (одно имя в реализации) — приоритет между «поиск по умолчанию» и `--config` фиксируем в спеке (обычно: `--config` > env > стандартные пути).

4. **Приоритет параметров MQTT**
   `(флаги CLI для MQTT) > (соответствующие env, совместимые с текущим `WB*MQTT*\*` где уместно) > (значения из JSON) > (встроенные дефолты)`. Это повторяет ожидание «сначала то, что явно задано для одного запуска».

5. **Форматы вывода**
   Текстовый режим по умолчанию (как сейчас). Имя флага для JSON: **`--json`** (без синонимов в спеке). При **`--json`** на stdout — **только** чистый JSON **без ANSI-кодов** (для пайпов и `jq`).

   **Текстовый режим — наглядность:** структурировать вывод (секции по устройствам, колонки/таблица контролов, краткая легенда в начале или в `--help`). Для **меток** аннотаций (**hidden**, **overridden** / **deviceType**, **skip**, **blacklist** / **whitelist**, **prefix skip**, **static devices**, **mappable** / **unmappable** и т.п.) использовать **ANSI SGR**: предпочтительно **цветной фон** (background) + контрастный цвет текста для коротких «бейджей», чтобы глаз цеплялся за категорию; фиксированная **палитра** по типу метки (документировать в README). Учитывать **`NO_COLOR`** (отключить цвета) и опцию **`--no-color`** (или эквивалент); при **не-TTY** stdout — по умолчанию без цветов, если не форсировано. Цель — **максимально удобный разбор** конфига глазами в SSH на контроллере WB.

   **Уточнение human-вывода (итерация после продакшен-прогона):** не дублировать на строке устройства **id в бейдже**, **prefix** и **exposureHint** отдельными токенами — вместо этого: строка-разделитель `── <deviceId> ──`, одна строка **matter:** с человекочитаемым итогом (префикс / нет mappable / white-black list / would register), строка **сводки** `controls: N total · M mappable · …`, опционально пояснение **static** `devices[]`, **note** если при prefix-skip на контролах всё ещё есть mappable (полный MQTT walk vs Matter). В начале — **Legend** и строка **Annotation flags** (фактические `includeHidden` и игнор префиксов), при отсутствии JSON — напоминание, что это дефолты. Пустой список контролов — явное сообщение. JSON-схема отчёта не меняется.

6. **Сводный «прогноз» экспозиции в Matter (опционально в одной строке на устройство)**
   По возможности вывести цепочку, согласованную с `registerWbDevice`: префиксы → наличие mappable контролов после skip/hidden → `validateDevice` → создание `WirenboardDevice` (детали в tasks/spec).

7. **Зависимости**
   Новых тяжёлых пакетов не вводить; минимальный разбор argv (ручной или лёгкий встроенный парсер без `commander`, если объём мал). Семантику **whitelist/blacklist** реализовать **одним** модулем `src/` (например `validateDeviceConfig.ts`), совместимым с `MatterbridgePlatform.validateDevice`, с юнит-тестом на те же кейсы; CLI и при необходимости тесты плагина импортируют его — **без дублирования** фрагмента в CLI. Зависимость CLI от полного `matterbridge` для инвентаризации **не** требуется.

## Risks / Trade-offs

- **[Risk] Конфиг лежит вне стандартного списка** (custom install).
  **Mitigation:** **`--config <path>`**; в `--help` перечислить порядок стандартных путей и env.

- **[Risk] Конфиг существует, но не читается (права, битый JSON).**
  **Mitigation:** явная ошибка с путём; exit code ≠ 0; не падать молча на дефолтах без предупреждения, если пользователь явно указал `--config`.

- **[Risk] Глобальная установка npm и путь `bin` на WB.**
  **Mitigation:** в README указать `npx <package> mb-wirenboard-verify-mqtt` как альтернативу `global` install.

- **[Risk] Терминал без 256/truecolor или нечитаемые комбинации фона/текста.**
  **Mitigation:** контрастные пары из стандартной 16/256 палитры; при **`NO_COLOR`** / **`--no-color`** — чистый текст; тест визуально в типичном SSH.

- **[Risk] Расхождение аннотаций CLI с реальным плагином** после правок в `module.ts`.
  **Mitigation:** одна реализация через общие функции; рефакторинг `module.ts` так, чтобы аннотации вызывали те же хелперы, что и регистрация; при изменении правил — один PR на модуль + вызовы платформы/CLI.

## Migration Plan

- После релиза: пользователи, привыкшие к `npm run verify:mqtt`, переключаются на `npm run verify:mqtt` (если оставлен как alias) или на имя бинарника; переменные `WB_MQTT_*` остаются поддерживаемыми для CI/совместимости.
