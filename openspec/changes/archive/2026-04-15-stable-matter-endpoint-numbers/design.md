## Context

Matterbridge регистрирует bridged endpoint’ы через `registerDevice()`; Matter.js назначает `EndpointNumber` при добавлении в агрегатор, если номер не задан явно. Плагин строит `WirenboardDevice` из `wbDevice.controls` (`Map`), обходит его в порядке вставки и в таком же порядке создаёт детей и вызывает `addChildDeviceType*`. Порядок первых MQTT retained сообщений может отличаться между запусками, из‑за чего меняется порядок регистрации и итоговые номера endpoint’ов. В `MatterbridgeEndpointOptions` поле `number?: EndpointNumber` поддерживается платформой и передаётся в Matter.js.

## Goals / Non-Goals

**Goals:**

- Стабильные **Matter endpoint numbers** для одного и того же набора WB-устройств и контролов при неизменной конфигурации и модели устройства на WB.
- Детерминированный **канонический порядок** построения: фиксированные слои (термостат → световые композиты → остальные mappable-контролы) и сортировка внутри слоя по имени контрола (или эквивалентное однозначное правило).
- Явное назначение номеров там, где автоматика Matter.js недостаточна или коллизии возможны.

**Non-Goals:**

- Специальная обработка `system` / `system__*` в первой итерации.
- Отдельная группировка по типу Matter только ради порядка (пользователь указал, что это не обязательно).

**Реализовано дополнительно:** порядок регистрации **между** разными WB-устройствами на агрегаторе — сортировка имён устройств в `registerDiscoveredDevices` (`compareCanonicalControlNames` по ключам `deviceMap`), чтобы порядок не зависел от порядка появления устройств в `Map`.

## Decisions

1. **Канонический список контролов перед сборкой**
   После детектирования термостата и lighting composites формировать список оставшихся mappable-контролов в порядке **сортировки по `ctrl.name`** (или по правилу `localeCompare('en')` для стабильности), а не в порядке итерации `Map`. Аналогично упорядочить массив композитов света по имени `switchControl` (или по вычисляемому `compositeId`).

2. **Явные `EndpointNumber` vs только порядок**
   Предпочтительно сначала добиться стабильности **через канонический порядок** добавления частей (минимум сюрпризов от Matter.js). Если тесты или рантайм покажут, что номера всё ещё «плывут», ввести **явные `number`** из выделенного диапазона (например хэш от `uniqueId` + смещение, или последовательность на плагин) с проверкой коллизий. Окончательная схема выделения — реализовать по результату спайка на целевой версии Matterbridge/Matter.js.

3. **Совместимость с semantic tags**
   Текущее требование: теги `tag: 1..n` для однотипных детей. После сортировки контролов порядок тегов должен соответствовать **каноническому** порядку детей (тот же индекс), чтобы не расходились «первый в Map» и «тег 1».

4. **Миграция**
   Уже сопряжённые контроллеры могут один раз увидеть новые номера после обновления — задокументировать как ожидаемый эффект; откат — откат версии плагина или сброс storage Matterbridge (тяжёлый).

## Risks / Trade-offs

| Риск                                                                                   | Митigation                                                                                       |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Коллизии явных номеров с другими плагинами или корневым агрегатором                    | Использовать диапазон/политику, согласованную с Matterbridge; тестировать на реальном aggregator |
| Разное поведение Matter.js при `number` задан vs не задан                              | Спайк + интеграционный тест на перезапуск                                                        |
| `detectThermostatControls` остаётся чувствительным к порядку при нескольких кандидатах | Отдельно ужесточить выбор кандидатов (tie-break по имени) в той же задаче или follow-up          |

## Migration Plan

1. Реализовать канонический порядок + тесты.
2. При необходимости добавить явные `number`.
3. Релиз-ноты: предупредить о возможной перенумерации endpoint’ов один раз после обновления.

## Verification on live MQTT

Скрипт **`scripts/real-mqtt-verify.mjs`**, запуск **`npm run build && npm run verify:mqtt`**, переменные **`WB_MQTT_HOST`**, **`WB_MQTT_PORT`**, при необходимости учётные данные. По умолчанию в корневом `AGENTS.md` указан продакшен-брокер для проверки. Скрипт подписывается на `/devices/#`, собирает модель как платформа, печатает канонический порядок контролов и число mappable — это проверка парсинга и сортировки на реальных retained сообщениях, не замена полного Matter e2e.

## Automated tests vs Matter.js endpoint numbers

Юнит-тесты с моком `MatterbridgeEndpoint` не воспроизводят аллокатор номеров Matter.js. Покрыто: детерминированный порядок детей и semantic tags при разном порядке `Map`; идентичность списков `id` endpoint’ов при последовательных `WirenboardDevice.create`; порядок вызовов `registerDevice` для нескольких устройств по каноническим именам. Совпадение фактических **`maybeNumber`** между перезапусками процесса Matterbridge остаётся предметом ручной/интеграционной проверки при необходимости.
